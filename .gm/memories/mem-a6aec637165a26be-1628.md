## Long-uptime latency CREEP = USB OUT-ring lag drift (UCA222/UAC1), fixed by b4d4f6c rate-trim (diagnosed 2026-06-24)

SYMPTOM: a build gets MORE LATENT the longer it runs (latency grows over hours of uptime). CAUSE: the USB OUT ring on the UCA222 (UAC1, synchronous) path had NO per-call rate correction before commit b4d4f6c -- AudioOutputUSB::outHandler (patches/output_usb.cpp) read the ring 1:1 from a fixed seed and only hard-resynced on OVERFLOW. UCA222 has no async-OUT feedback PI (unlike UAC2/Tascam), so the engine clock (44100 internal resampled to 48000) vs the device DAC clock differ slightly -> the OUT-ring 'avail' (buffered samples = output latency) drifts MONOTONICALLY upward over time toward the overflow edge (~OUT_RING_SIZE-64 ~4032 samp ~84ms), a slow sawtooth (ramp up, snap at overflow with a glitch, repeat). Perceived as growing latency over long uptime.

FIX (already shipped, in the deployed kernel): b4d4f6c added a deadband(+-32) skip/repeat rate-trim toward OUT_RD_TARGET=96 (~2ms) in outHandler for the UAC1 path (g_audioUAC2==0) -- pins the OUT lag low so it CANNOT creep. The user's prior flash predated b4d4f6c; the current build fixes it.

RULED OUT as creep sources: IN ring already has the same drift correction (input_usb.cpp IN_TARGET_LAG=96 + IN_DEADBAND=48 + fractional trim); sampler m_ageCtr unsigned wrap ~497 days + cosmetic (voice-steal order only); apcEffectsProcessor m_delayReadPos modulo-bounded; UAC2 s_outBias clamped +-fbRate/50 and UAC2-only. The OUT ring was the ONLY uncorrected one. See [[looper-uca222-latency-double-buffer-uac2-gate]] [[looper-audio-architecture]].
