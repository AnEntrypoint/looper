## Resolved mutable: latched-record-should-not-backdate

CONFIRMED. g_pendingPressTicks is set ONLY in the APC cmd drain (apcKey25.cpp:278) when a command is first processed (where the deferred RECORD pending is SET). The actual latch runs later in loopMachine::updateState() (line 834 -> pTrack->updateState -> _startRecording), a SEPARATE Core-2 call; g_pendingPressTicks is NOT refreshed for the latch, so it holds a stale/arbitrary press tick. _startRecording then m_recStartBlock=cbBackdatedBlock(stale) (backdates content to the wrong/earlier instant) and startPhase=m_masterPhase-backBlocks re-snapped round-to-nearest (lands on a neighboring beat) => the consecutive loop starts late / off the first-loop downbeat. FIX: in _startRecording, when pTheLoopMachine->m_masterLoopBlocks > 0 (a latched consecutive loop — the latch in loopMachine fired exactly at m_masterPhase%gridStep==0, the true start, with NO latency left to compensate because the wait-for-grid absorbed it): set m_recStartBlock = g_cbWriteBlock (current head, no backdate) and m_recordStartPhaseOffset = pTheLoopMachine->m_masterPhase (the latch beat), with NO re-snap. When m_masterLoopBlocks == 0 (FIRST loop, immediate, no latch): keep the sample-true backdated press (m_recStartBlock=cbBackdatedBlock(press), offset derived, no snap). This removes the stale-backdate + double-snap drift. Witness: apcKey25.cpp:278 sole g_pendingPressTicks writer; loopMachine.cpp:834 latch in updateState (different call); loopClip.cpp _startRecording backdate+resnap.
