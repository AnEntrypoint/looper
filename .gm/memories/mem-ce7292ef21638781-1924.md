## Looper<->esp32 Ableton Link not syncing = looper kernel built WITHOUT LOOPER_ENABLE_WLAN; WLAN kernel boot-hangs (2026-06-22)

Symptom: looper didn't start a 'ticker' AP and didn't join the esp32's AP. ROOT CAUSE: the deployed looper kernel had WLAN+Link COMPILED OUT -> live :4445 WLAN = 'wlan=disabled link=no' = zero radio activity. The no-output USB fix kernel was built with LOOPER_USB_AUDIO=1 LOOPER_OTG_AUDIO=1 but NOT LOOPER_ENABLE_WLAN, and kernel.cpp #ifdef LOOPER_ENABLE_WLAN gates linkInit + the entire bring-up. The looper's symmetric host/join LOGIC IS correct + present (kernel.cpp wlanServiceBringUp: JoinOpenNet('ticker') 3x then CreateOpenNet AP fallback; wlanApYieldTry yields to a lower-BSSID co-host / re-hosts; wlanStationRejoin; wlanFallbackToAP) -- just not compiled in. The esp side (../esp-idf-link) IS correct + symmetric: main.cpp scans 'ticker' -> join STA if found else wifi_start_link_ap; wifi_config.cpp supervisor re-scans/re-hosts/yields on lower BSSID. So neither side's logic is the bug. BLOCKER: building the looper WITH LOOPER_ENABLE_WLAN=1 (make ... LOOPER_USB_AUDIO=1 LOOPER_OTG_AUDIO=1 LOOPER_ENABLE_WLAN=1; or build-local.ps1 -Wlan -> kernel7l-wlan.img) produces a kernel that HANGS AT BOOT before network on this Pi (deployed+rebooted -> :4445 silent >180s) -- the known radio/plan9 SDIO bring-up wedge (HARDWARE-VALIDATION-PENDING). Pre-network so syslog/:4445 unavailable; locating the wedge needs HDMI/UART console at boot. Recovery: keep the safe USB-only kernel on the netboot path (output works, WLAN off); power-cycle to recover from the hung WLAN kernel. To actually get Link working, the WLAN boot-hang must be fixed first (bound/guard radio init so a hang -> timeout+continue, or move radio init off the boot path). The wifi SSID both sides use is 'ticker' (open). See [[looper-wlan-link-full]] [[looper-no-output-real-cause-usb-build-flag]] [[pi-netboot-tftp-paths]].
