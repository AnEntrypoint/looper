## Looper MIDI mapping is data -- midiMap.h atomic controller profile

Every in/out MIDI control is an atomic controller-agnostic record. struct MidiInputMap keyed on (statusType,channel,data1Lo..data1Hi)->logical MidiAction+valueMode+param; struct MidiOutputMap = logical MidiFeedbackState->note+velocity. Looper logic speaks logical actions (MA_PAD, MA_LIVE_PITCH_NOTE_CH1, MFS_LOOPER_RECORDING...); controller physical addresses+LED colors live ONLY in g_activeProfile (MidiControllerProfile bundling tables+VU thresholds+mod-deadzone). g_apc25Profile = default, byte-identical to former hard-coded behavior (load-bearing no-op invariant). midiMapResolveInput/midiMapResolveOutput/midiMapDecodeValue. MidiValueMode {MV_ABSOLUTE,MV_RELATIVE_TWOS,MV_RELATIVE_SIGNBIT,MV_TRIGGER} for endless encoders. Output side LIVE config-driven (apcKey25Transpose.cpp::_updateGridLeds -> _ledVel -> midiMapResolveOutput). Compiled-in default; FatFs mounted for future SD:/firmware/midimap.txt override via g_activeProfile indirection. scripts/test-midi-config-parity.cpp ALL PASS (full event matrix == legacy). NOTE: the gamepad does NOT use midiMap -- it synthesizes APC MIDI bytes into handleMidi directly. See [[looper-usb-midi-host]].
