## Looper second-loop OFFBEAT: playback reads the CLIP BUFFER, not the ring (commit follows 470c336)

Symptom: first loop perfect, SECOND recording played back shifted to the offbeat from how it was recorded. Root cause: loopClipUpdate playback reads pp_main=getBlock(m_play_block) = the CLIP BUFFER, which was filled incrementally DURING recording from the beat-snapped m_recStartBlock (buffer block i = ring m_recStartBlock(record-time)+i). _startEndingRecording then did a stop-time FLOOR: m_recordStartPhaseOffset-=floorBack AND m_recStartBlock-=floorBack. But changing m_recStartBlock AFTER the buffer is filled is INERT (playback uses the buffer, not cbBlockPtr) — so only the PHASE moved, shifting play_block=(masterPhase-offset)%L off the already-recorded audio by floorBack = the offbeat. FIX: REMOVED the stop-time floor entirely. recordStartPhaseOffset is set ONCE at _startRecording, beat-snapped (M/16) and tied to m_recStartBlock (same snapDelta), so it already names buffer block 0. The beat-snapped offset is coherent with every quantized L (all {M/8..8M} are multiples of M/16) so play_block hits 0 at the recorded downbeat and every L-boundary — no floor needed for sync. RULE (load-bearing): once the clip buffer is recorded, m_recStartBlock is inert for playback; never try to re-align a consecutive loop by mutating m_recStartBlock or flooring recordStartPhaseOffset at stop — the only valid anchor is the record-start beat-snap that the buffer was actually filled against. Host test scripts/test-consec-lock.cpp proves play_block==0 at offset reads the recorded downbeat and that the old floor would have shifted it.
