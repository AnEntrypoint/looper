## Looper consecutive loop starts LATE: latched record must NOT backdate (commit follows 933838c)

Symptom: second loop started a little later, didn't coincide with first-loop start. Root cause: a CONSECUTIVE record is deferred to the pending-record LATCH (loopMachine::updateState), which fires _startRecording EXACTLY at a beat downbeat (m_masterPhase%gridStep==0). But _startRecording still did m_recStartBlock=cbBackdatedBlock(g_pendingPressTicks) + startPhase=m_masterPhase-backBlocks then round-to-nearest re-snap. TWO faults: (1) g_pendingPressTicks is STALE at latch time - it is set ONLY in the APC cmd drain (apcKey25.cpp) when the pending was SET, and the latch is a LATER separate Core-2 call that never refreshes it; so the backdate used an arbitrary old tick. (2) the wait-for-grid latch ALREADY absorbed the press->grid latency, so there is no latency to compensate; backdating + re-snap shifted the start to a neighboring (later) beat. FIX: _startRecording branches on m_masterLoopBlocks. M>0 (latched consecutive): m_recStartBlock=g_cbWriteBlock, m_recordStartPhaseOffset=m_masterPhase (the latch beat) - NO backdate, NO snap. M==0 (first loop, immediate): keep cbBackdatedBlock(press) sample-true + derived offset. RULE: only the IMMEDIATE first loop backdates (compensates press->process); a grid-LATCHED loop's true start IS the latch instant (current write head + current masterPhase) - never backdate or re-snap a latched start. Host test scripts/test-consec-lock.cpp: latched offset==latch beat, play_block==0 at offset (coincides with first-loop start).
