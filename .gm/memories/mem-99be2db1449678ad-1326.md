## Looper consecutive loop SILENT: latched anchor read the unwritten ring head (commit follows d9800b9)

Symptom: second loop reached PLAYING (FSM sound, running==1, num>0) but produced NO AUDIO. Root cause: the latched-consecutive _startRecording set m_recStartBlock=g_cbWriteBlock. But cbWriteBlock writes dst=cbBlockPtr(g_cbWriteBlock) THEN g_cbWriteBlock++, so g_cbWriteBlock is the NEXT-to-write block (~180s-old/silent). loopMachine::update order is (609)cbWriteBlock -> (655)updateState[latch->_startRecording captures g_cbWriteBlock=W+1] -> (664)track update[clip records cbBlockPtr(W+1+0)] = the unwritten head = SILENCE. The clip recorded silence -> played nothing. FIX: m_recStartBlock=cbBackdatedBlock(0) (press_ticks==0 -> fixed-lag only = g_cbWriteBlock - CB_FIXED_LAG_SAMPLES/AUDIO_BLOCK_SAMPLES), a WRITTEN history block with the same fixed ring lag the first loop uses; phase stays m_masterPhase. RULE: ALWAYS anchor clip content to a WRITTEN ring block (cbBackdatedBlock, which returns wr-backBlocks with backBlocks>=1), NEVER raw g_cbWriteBlock (next-to-write). The first loop was always correct (cbBackdatedBlock(press)); only the latched consecutive shortcut to g_cbWriteBlock was silent. Diagnosis required a full FSM sim (test-consec-fsm) to rule OUT the state path and isolate it to the content source.
