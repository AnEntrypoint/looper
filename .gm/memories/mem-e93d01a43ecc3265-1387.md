## MIDI mapping is data: midiMap.h atomic controller profile (commit follows)

Every in/out MIDI control is an atomic controller-agnostic record in midiMap.h. struct MidiInputMap = one input keyed on (statusType, channel, data1Lo..data1Hi) -> logical MidiAction + valueMode + param. struct MidiOutputMap = one MidiFeedbackState -> note+velocity. Looper logic speaks logical actions/states; controller physical addresses + LED colour scheme live ONLY in the default g_apc25Profile. Swap g_activeProfile (MidiControllerProfile: both tables + vuMid/vuHigh + mod-deadzone) for a non-APC controller, no code change. g_apc25Profile is byte-identical to former hard-coded behavior (load-bearing no-operational-change invariant; primary target = APC Key 25). Output side LIVE config-driven: _updateGridLeds -> _ledVel -> midiMapResolveOutput; live-engage LED in apcKey25.cpp::update too. Missing state -> OFF (graceful, no stuck LED). MidiValueMode {MV_ABSOLUTE, MV_RELATIVE_TWOS, MV_RELATIVE_SIGNBIT, MV_TRIGGER} via midiMapDecodeValue supports endless encoders. Storage: compiled-in default (zero deps), optional SD override via FatFs (patches/kernel.cpp f_mount) by swapping g_activeProfile. Witnessed scripts/test-midi-config-parity.cpp ALL PASS (full note-on+CC matrix all channels, output velocity parity, relative decode, partial/null profile); firmware build clean kernel7l.img 1060748B.
