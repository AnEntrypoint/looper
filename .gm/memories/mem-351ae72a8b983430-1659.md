## Resolved mutable: min-fix-reintroduces-original-truncation-for-full-rate-devices

Confirmed via re-reading dwhcixferstagedata.cpp TransactionComplete (lines 267-289) precisely: for a non-split isochronous multi-packet URB, EVERY packet's TransactionComplete call (including all but the last) takes the early-return branch at line 287 without ever reaching the non-isochronous m_nTransferSize-vs-m_nTotalBytesTransfered reconciliation at line 291-296. m_nTransferSize is reassigned to EACH new packet's individual declared size at line 279 as processing advances, and is NEVER restored to the sum/original full-URB size. So by stage-complete, m_nTransferSize holds only the LAST packet's small individual size while m_nTotalBytesTransfered correctly holds the accumulated sum across all N packets. GetResultLen() (line 578-586) compares these directly: m_nTotalBytesTransfered > m_nTransferSize is true, so it returns just m_nTransferSize (one packet's worth) -- CONFIRMS my original analysis: GetResultLength() for the UAC2 N=8 batched path genuinely discards ~7/8 of the real accumulated captured data, it is not merely 'clamped but still substantially correct'. Therefore min(GetResultLength(), m_nInSubmitBytes) DOES reduce to the severely truncated GetResultLength() value in the common full-rate case, defeating the batching throughput fix -- my mutable's concern is CONFIRMED VALID, the min()-based EMIT must be replaced with a different design that trusts m_nInSubmitBytes as the primary source (to preserve AIR 192|4's fix) while adding a SEPARATE, correctly-scoped safety margin against the short-packet over-read risk that caused the US-2x2 buzz.
