## 2026-07-10 — Telemetry taps that all sample the same point in a pipeline can't disprove a downstream bug
Goal (G): Find the real source of a periodic 500Hz buzz artifact confirmed via a real user recording, on the Looper's USB-audio input path.
What drifted / what went wrong: built and live-tested four separate raw-input diagnostics (ZCR, RMS energy, raw waveform capture, per-slot completion counters) across several build/deploy/reboot cycles, all showing clean results -- but all four taps sampled the SAME point in the pipeline (usbaudiodevice.cpp InCompletion, before loopMachine ever touches the signal). Confirming "clean" four times at one tap point was mistaken for ruling out the bug generally, when it only ruled out that one stage. The actual WAV recordings this project produces (usbWavRecorder.cpp, loopDump.cpp) both capture from loopMachine.cpp's WET/post-effects m_input_buffer, a different point entirely -- a fact only surfaced by directly reading loopDump.cpp's source, not assumed.
Fix / resolution: added the same ZCR/energy telemetry at the actual WAV-capture tap point (loopMachine.cpp, right before cbWriteBlock) so raw-input and wet-signal can be compared in the same live window -- directly testing whether an artifact is introduced inside loopMachine's own processing (live-pitch/microrepeat/filters) rather than at the USB/ring layer.
Generalizes to: when multiple diagnostic probes at one tap point all come back clean but a real symptom persists, the next move is not another metric at the SAME tap point -- it's confirming (from source, not assumption) where the artifact-under-investigation is actually observed/produced, and instrumenting THAT point instead. A clean reading only rules out the segment of the pipeline it actually samples.

## 2026-07-10 — Found and fixed the actual buzz root cause via BBCR checkpoint + real waveform inspection
Goal (G): Find and fix the real source of the Looper's UAC2 USB-audio buzz, confirmed via live hardware, not more speculative telemetry.
What drifted / what went wrong: nothing this cycle -- this is the resolution of the drift recorded in the prior lesson entry. After five disproven hypotheses across two tap points, the temptation was to keep guessing at a sixth. Applied BBCR instead: stopped, went back to the one piece of real ground truth (the user's buzz.wav recording) and to live RAWD captures of actual waveform data (not scalar statistics), and found a precise, repeatable corruption signature (-4608 at a consistent array index) that static reasoning and aggregate statistics had both missed.
Fix / resolution: traced the -4608 signature to InCompletion's UAC2 decode loop reading m_InBuf contiguously, when StartInRequest's AddIsoPacket(pktSize) x8 actually lays the URB out as 8 fixed pktSize-byte slots (one per microframe) with real data only partially filling each slot. Rewrote the decode loop to walk per-microframe at each packet's own offset. Live-verified: the exact corruption signature present in 5/5 pre-fix RAWD captures is absent in 8/8 post-fix captures.
Generalizes to: when scalar/aggregate telemetry (rates, means, crossing counts) all read clean despite a confirmed real symptom, the bug may be a small-fraction, structurally-localized corruption (e.g. 1-2 bad samples per ~48-sample batch) that averages wash out entirely. The fix was found by inspecting REAL WAVEFORM SAMPLES directly (RAWD raw capture + the user's own recording), not by adding another aggregate statistic. When telemetry-based hypothesis testing stalls after 2-3 rounds, switch tools: go to raw data inspection, not another summary metric.
